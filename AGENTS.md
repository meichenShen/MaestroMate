# MaestroMate project conventions

- The active website is in `web/`; preserve the research documents, assets and `old version/`.
- Anonymous feedback belongs to `web/src/features/feedback/`, `worker/` and the private Sites D1 binding. Never expose a public feedback read API, commit real messages/email addresses, or show receipt without a server acknowledgement. Generate and commit Drizzle migrations; runtime requests must not change schema. Local SQLite databases stay in ignored `.tmp/`.
- Keep navigation, work introduction, contextual notes and player as separate components. Keep each activity in its own feature directory.
- Shared audio belongs to one provider above the activity switch. Never mount another audio element for a question or remount it when switching activities.
- Put recording-specific content, questions, chapter times and attribution in `web/src/content/`. Changing a recording requires reviewing every timestamp.
- Use `web/src/styles/tokens.css` for design variables and `layout.css` for column widths and responsive breakpoints. Avoid cross-feature CSS dependencies.
- Put short-lived downloads, QA screenshots, logs and packaging artifacts under the ignored `web/.tmp/` directory. Do not create dated copies of the source tree; use Git history.
- Do not commit dependencies, build outputs, caches, secrets or test artifacts. Keep original source material and Git history. Only remove verified reproducible artifacts belonging to this project; never clear app-wide or other projects' caches.
- Keep browser QA and the editing guide current after behavior changes. Public publishing is authorized for this demo; preserve that audience on updates.
- Approved visual direction: Outfit + Onest, mainly black, readable normal-case copy and large rendered imagery. Keep artwork in the programme and keep its browsing vertical.
- First-entry choices have two primary pictorial actions. Just looking is a subordinate action only in that dialog; do not turn it into a homepage feature.
- Real-time fish rendering belongs in `web/src/rendering/` and `AquariumView`; pre-rendered illustrations belong in `web/public/images/`. Preserve that distinction in credits and claims. Model/source licenses live with the assets.

- Listen, Chat and Play are independent routes/features. Program is an optional guided route through them; show progress/next only for explicit Program URLs.
- Retain ordered conversation turns above route switches; do not replace the thread with one answer. Live AI is now explicitly authorized: keep it opt-in, sourced, bounded and server-only.
- Home-only scene snapping must respect dialogs, nested chat scrolling and reduced motion. Keep libraries and rooms freely scrollable.
- Theatre art is original texture-free3D geometry. Large icons may draw their strokes. Do not reintroduce generated theatre/portrait/environment rasters; static fallback should be captured from actual rendering.

- Approved baseline is Git tag `baseline/rooms-v5`. Refine its design; avoid unrelated redesigns. Desktop is the current priority; keep mobile functional.
- Use light periwinkle/peach/yellow/blue accents and neutral violet/ink surfaces. Do not restore green UI panels.
- Hover may reveal descriptions, but names and stable accessible entry targets remain visible; keyboard focus reveals the same information and touch keeps it readable.
- Composer replies are labelled fictional first-person adaptations with institutional biographical sources, never fabricated historical quotations. Nested conversation scrolling must release the page at thread boundaries.

- Latest palette comes from the user's LOL screenshots: #45D9FD cyan, #EE2560 rose, #FFDA8E amber, with #A593E0 lavender and #80D4F6 sky as supporting colours. Earlier interim purple/coral tokens are superseded. No green UI or default model material.
- Desktop activity pages must fit one viewport above the measured player: core actions never require document scrolling. Keep three case overviews, animate the active fixed answer stage, and retain previous/next plus feedback in place. Source notes open in a separate dialog. Chat history may scroll internally.

- Question prompts are essential and always visible. Case navigation is a local horizontal rail with data-derived counts; it never replaces the fixed answer stage with a long page.
- Hall passive hover is gentle; wide damped drag starts only on a mesh hit. Keep orchestra resources registered through the existing factories and reuse instanced geometry.
- Homepage settling is proximity-only; never restore mandatory page correction. Letter arrivals and Program fireworks are finite, accessible and reduced-motion-safe. Explicit Restart Program resets answers/chat and cancels pending replies without remounting audio.
- Preview cards must avoid every icon, with readable contrast; keep the original stationary entry targets.

- Answer layout is owned by `web/src/features/detective/detective.css`: question/audio, choices and feedback/action are separate rows. Keep every control inside its card and separated from previous/next at short desktop heights, including600px with the expanded error player.
- The theatre opening follows pointer direction; passive span is about34°. Preserve mesh-hit drag, damping and durable interruption behavior. Program fireworks use the existing renderer/camera; no second canvas, infinite animation, external runtime asset or decoration under reduced motion.

- Work-specific Play content and evaluation live in `web/src/content/play/`; the active visual workspace is `web/src/features/workshop/`. Only registered works may resolve, including prototype-like URL names. New works require their own researched games and reviewed recording integration. Keep original practice sounds distinct from recorded passages. Per-work/game progress counts checked successes, resets on Program restart, and never gates exploration.
- Music Pool uses a rimless soft-edged surface; do not restore decorative torus/body/outer stroke. Fish echo and free painting share the existing synth and must cancel stale startup/voices on mode/Guide/hide/navigation. Preserve44px-plus separate HTML targets and fallback, with no compulsory drag.

- Current Play uses `web/src/features/curriculum/` and `web/src/content/curriculum.ts`: Explore a piece / Music lessons / Create & play. Learn, two Try checks, and Make are distinct screens in the fixed desktop stage. Keep recording-backed work content separate from general lessons and original synth examples. The v14 twelve-game workshop is archived source, not the active navigation.
- Prepared Chat knowledge and sources live in `web/src/content/knowledge/`. Keep full suggested questions visible; only supplementary hints may rely on hover. AI is now resumed with Qwen; worker/chat.ts owns provider calls, typed knowledge/retrieval owns reference context, and private D1 stores quota metadata only. Never put keys in VITE variables or deploy a Cloud proxy placeholder as a vendor secret. Unit progress is visit-local and counts two checked answers plus a completed valid creation; audio cancellation never marks completion.

- v17 supersedes v15's forced making gate: active Play has independent Explore a piece / Music lessons / Create & play routes. Learning units live in curriculum.ts + curriculum-extra.ts, with three varied checks, URL-based Learn/Try/Complete steps, local Back and one central next-action dock. No lesson requires creation for completion. CreationBoard is archived; independent free studios live in features/creation/, and Pool/studios return to #play/create. Keep visit-local studio drafts separate from curriculum progress. Source accuracy and visible reduced-motion-safe success feedback are required.
- Latest Chat supports English and Chinese with an explicit question-area language selector, per-turn language and Chinese retrieval aliases. Keep model selection and the AI switch visible beside asking; first activation retains a privacy dialog. The two primary Chat panels are the illustrated biography and conversation. Course titles use explicit chapter subjects, Exit lesson remains independent of step Back, and home order is Listen → Chat → Play.
- Site-wide language now lives in web/src/i18n/: top-header English/中文 preference persists across navigation/reload and drives Chat language. Use useLocale() and t() for UI/source-owned copy; add Chinese catalog entries for new text. Never translate business IDs, form values, user-authored questions or stored AI responses. Language changes must not remount audio or reset quiz/studio state. Keep Chinese headings wrappable and dynamic accessible names localized.
- Chinese UI uses the reviewed shared catalogue even inside Chat; avoid duplicated `zh ? literal : literal` branches for static copy. Use plain Chinese, precise music terms and normal reading widths. SC font subsets and OFL provenance live in `web/public/fonts/`; the optional regeneration tool is `web/scripts/subset-chinese-fonts.py`. AI user/answer snapshots remain untranslated.
- Chat retrieval must rank the current topic before historical context, expand Chinese aliases in both current and previous questions, and retain factual/editorial boundaries. Unknown private feelings must remain unknown; a small reference collection is not proof that no historical record exists. Add source-backed notes and regression questions together.
- Creative piano samples are the credited eight-note Salamander subset in `web/public/audio/piano/`; verify hashes before building. Samples/synths share PoolAudio's cancellable context, with release-aware completion and no queued burst after loading. Curriculum timbre examples retain their original synthetic meaning. Preserve independent drum tracks, visit-local creative instrument/backing drafts, and sample-failure recovery when changing creation controls.
- Chat's compact asking dock and optional expanded reading layout must preserve thread DOM, draft, open citations and source access. Keep long-reply start/end reachable above the player; selecting the latest turn must not depend on :last-of-type when a typing indicator is present. Musical reasoning/teaching examples may explain principles without being invented autobiographical memories; do not fill a composing question with unrelated editing/biography facts.
